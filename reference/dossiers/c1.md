# c1: client.dll .text 0x8310-0x4e7ab

The start of Rocket Crowbar 2's client library: the predicted weapons (crossbow through
tripmine, compiled from the same `dlls/*.cpp` as the server), ev_hldm and RC2's events,
hl_baseentity's stubs, hl_weapons, the voice code and CHudAmmo. Reconstructed by the c1 agent with
two helpers (events, HUD); their reports are folded in below.

## How the client reads

- **Layout.** Every client member after CBaseEntity's early part sits at the server's offset
  plus 0x200 (m_fInAttack 0x24c, m_pPlayer 0x28c, m_iId 0x294, m_iClip 0x2c4,
  m_flNextTertiaryAttack 0x2b0, m_flNextQuaternaryAttack 0x2b4, m_flTimeWeaponIdle 0x2b8; player
  m_rgAmmo +0x6e0, m_flNextAttack +0x46c, m_flNextAmmoBurn +0x860, m_iRidingIndex +0x89c). The
  0x200 bytes are a buffer at +0x20 that the client's SetThink copies the think function's name
  into (with SDK's FunctionCheck): a debug ThinkSet, not reconstructed (DEVIATIONS below).
- **Vtables.** The 14 weapon vtables (116 slots) and the player's are the server's slot for
  slot; a helper script (Tools, below) pairs them per class and points at our source.
- **rc2.ini.** The client has the server's whole table (same 1113 records at .data 0x13e6e0,
  values at 0x10210aa8 + 8*i) and reads it where the server does, so `RC2Pref()` is used on both
  sides; the server packages' client fallbacks to SDK constants are gone.
- **Event flag.** The server's `g_fRC2PlayWeaponEvents` / `g_iRC2WeaponFrame` /
  `g_iPlayWeaponEvents` / p2's `g_runfuncs` (all rc2.dll .data 0x181434) are the client's
  g_runfuncs (.data 0x206068); each weapon file maps its name to g_runfuncs on the client.
- **Underwater bit.** The server's several names for 0x95860 (PlayerCanFireUnderwater,
  RC2_PlayerFiresUnderwater, RC2PlayerWaterWeapons, CanFireUnderwater) are the client's
  PlayerHasAttrFlag200 (orig client 0x3ba60), reading the predicted player's m_iAbilities.
