## The loose ends

**Weapon pickup (a3's note), `CBasePlayer::AddPlayerItem` (orig 0x9d150, player.cpp).** The
original's tail is SDK 2.3's with RC2's riders: `AddToPlayer`, `PlayerGotWeapon`, `CheckRespawn`,
insert into the slot list, `FShouldSwitchWeapon`/`SwitchWeapon`, return 1; else the
gEvilImpulse101 kill or `RidersAddPlayerItem`. Its duplicate branch was already the original's.
halflife-updated had moved `ExtractAmmo` here after the insert, sent `SendSingleAmmoUpdate` at
once, and sent WeapPickup for every weapon that isn't exhaustible unless `m_bIsSpawning`. In the
original only the eight weapons whose `AddToPlayer` sends it announce a pickup (python, crossbow,
egon, gauss, hivehand, mp5, rpg, shotgun; vtable slot 80 in `vtables-rc2.tsv`): the crowbar
(0x304a0), glock, hand grenade, snark, tripmine and satchel never do, and nothing is held back while
spawning. Put back:

- AddPlayerItem's tail as above; `CanAddToPlayer` stays in front of `AddToPlayer` (halflife-updated's
  split, which RC2's crowbar refusal already uses), so the split is style.
- `CBasePlayerWeapon::AddToPlayer` (weapons.cpp) calls `ExtractAmmo(this)` at its end: SDK 2.3's
  AddWeapon, so the ammo is given before the weapon joins the list, as in the original.
- The eight weapons send WeapPickup after the base (`#ifndef CLIENT_DLL`; nothing calls them in
  the client). `CRpg::AddToPlayer` is back (weapons.h, rpg.cpp).
- `CHgun::AddToPlayer` (hornetgun.cpp, RC2's, orig 0x65110): the original sets
  `m_rgAmmo[PrimaryAmmoIndex()]` to the max carry pref after the base gave the default ammo;
  halflife-updated's arrangement raised `m_iDefaultAmmo` before the base. Same end count, but the
  AmmoPickup number differed. Original order back.
- Dead after this, removed: `CBasePlayer::m_bIsSpawning` (player.h, and its set/reset in Spawn) and
  `CBasePlayer::SendSingleAmmoUpdate` (player.h, player.cpp).

The comments in crossbow, python, egon, gauss and shotgun said halflife-updated's AddPlayerItem sent
"that same message ... one message either way"; that was wrong (crowbar and glock got one too, and
spawning got none), and they are replaced.

**m_ForceSendAnimations (a1's note).** The original's `SelectItem` (0x9c180) and `SwitchWeapon`
(0x9eac0) call Holster, set the item and call Deploy (and UpdateItemInfo in SelectItem) with nothing
around Deploy. Reverted in both, as a1 did in SelectLastItem. `SwitchWeapon` keeps
halflife-updated's `pWeapon &&` before `CanDeploy` (guard: the original calls CanDeploy through the
pointer unchecked). With no writer left, `CBasePlayerWeapon::m_ForceSendAnimations` (weapons.h) is
removed and `SendWeaponAnim` (weapons.cpp) skips the predicting client on `UseDecrement()` alone,
SDK 2.3's test.

**Unread members (a2's note).** `CBaseMonster::m_flLastYawTime` (basemonster.h) and
`CFlyingMonster::m_flLastZYawTime` (flyingmonster.h) had no reader or writer left and are in no save
table; removed. (a3 had already removed the ichthyosaur's `m_flLastPitchTime`.)

## Odd

- The present table's rva is where the shared SDK body first turns up, so for six rows it is another
  function's code: the three grenade Precaches, FAllowMonsters and EMIT_GROUPNAME_SUIT are RC2's
  own at other addresses, and the AddToPlayer group's 0x2ae70 is the crossbow's. A present row needs
  the named function's own address found before its body is read against SDK 2.3.
- The loose mode doesn't fold a changed return type (`int X::F` to `bool X::F`): the lookahead after
  `int|bool` wants no space, and the normalizer keeps the space before the class name. That is why
  most of this table is a bare bool return.
- `CBaseMonster::ChangeYaw`'s and `CFlyingMonster::ChangeYaw`'s revert comments (monsters.cpp,
  flyingmonster.cpp) still name the removed members; they describe what halflife-updated did.
