Beyond the rows, in the same files:

- `COsprey::TakeDamage` and `COsprey::Update` removed (osprey.cpp). RC2's COsprey vtable has
  CBaseMonster's TakeDamage (0x20f60); halflife-updated's override made the attacker the enemy and
  the state combat for the AI triggers that Update ran. Reverting the Update calls left both with
  no purpose in SDK 2.3's behavior.
- `CBasePlayer::GiveAmmo` (player.cpp, orig 0x9d4c0, RC2's): halflife-updated's "give the
  exhaustible weapon with its ammo" block removed. The original's decompile has no such call (cvar
  check, index, add, AmmoPickup, TabulateAmmo, riders). This is the only reader of
  AddAmmoNameToAmmoRegistry's weapon name (a1's unclear row), so that registration is now inert.
- `CBasePlayerWeapon::DoRetireWeapon` / `CallDoRetireWeapon` (weapons.cpp, weapons.h) are left
  defined but nothing calls them; removing them would touch weapons.h and the client's
  hl_baseentity.cpp stubs.

## For DEVIATIONS.md

- Kept halflife-updated guards: Nihilanth's target-name buffers are 128 (NextActivity,
  HandleAnimEvent), CMultiManager::KeyValue bounds UTIL_StripToken, COsprey::FlyThink checks
  m_pGoalEnt, CTriggerCamera::Use returns with no player 1, RemovePlayerItem clears m_pLastItem
  when the active item goes, Save/RestoreGlobalState check the save data.
- Kept: the player's suit test and weapon bits go through m_WeaponBits (HasSuit, SetWeaponBit),
  mirrored into pev->weapons below bit 32.
- Kept, single player only: spserver.cfg exec, trigger_camera's m_hViewEntity, CStripWeapons'
  local player lookup, the changelevel transition code.
- Unclear, kept: a weapon item stops its FallThink when a player holds it (FallThink's `else if
  (m_pPlayer)` and AttachToPlayer's SetThink(NULL)). In SDK 2.3 an item picked up mid-air keeps
  FallThink; if FL_ONGROUND were ever set on it while held, Materialize would make the held weapon
  a touchable trigger again (respawn sound, and a touch would Kill it through AddDuplicate while it
  is still in the inventory). Whether the engine sets FL_ONGROUND on a MOVETYPE_FOLLOW item decides
  it; not tested.

## Odd

- `CBasePlayer::SelectItem` and `CBasePlayer::SwitchWeapon` (player.cpp) set m_ForceSendAnimations
  around Deploy, as a1 reverted in SelectLastItem. Neither is in sdk-drift.tsv (RC2-modified or not
  matched), so not changed here; the merge should make the same call as a1.
- `CBasePlayer::AddPlayerItem` (orig 0x9d150, RC2's) still carries halflife-updated's pickup flow:
  CanAddToPlayer, list insert before ExtractAmmo, SendSingleAmmoUpdate, no WeapPickup while
  m_bIsSpawning or for exhaustible weapons. Worth checking against the decompile like GiveAmmo.
- GetAutoaimVector tests `g_psv_allow_autoaim != 0` (the pointer, not its value); harmless here.
- SDK 2.3's IsUseable (now back) reads m_rgAmmo[-1] for a weapon with no ammo type before
  `iMaxAmmo1() != -1` short-circuits it; an in-object read, no crash.
- CBaseMonster::RunAI's SDK 2.3 bug, now back: gagged monsters still idle-talk and swimming ones
  (FL_SWIM, e.g. ichthyosaur) never do.
